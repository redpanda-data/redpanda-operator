## [v26.2.5](https://github.com/redpanda-data/redpanda-operator/releases/tag/charts%2Fredpanda%2Fv26.2.5) - 2026-10-22
### Changed
* The configurator and fs-validator script volumes on the Redpanda StatefulSet are now named `configurator` and `fs-validator` rather than `<fullname>-configurator` and `<fullname>-fs-validator`. Volume names are pod-local, so only the volume and volumeMount entries change; the Secrets they project are still named after the release and are untouched. This also fixes the configurator volume name exceeding Kubernetes' 63 character limit for releases whose fullname is 51 characters or longer.

  Upgrading an existing release changes the pod template and therefore rolls the brokers. If you override either of these volumes or volumeMounts through `podTemplate`, note that those lists are merged by name: an override keyed on the old `<fullname>-` prefixed name will silently stop matching and must be re-keyed to the new name.
* `values.schema.json` now emits each type once under `$defs` and references it, rather than inlining every use site. The schema is unchanged in what it accepts, with one exception noted below, and is 3-5x smaller -- which every `helm template`, `helm install`, and `helm upgrade` pays to compile.

  Arrays nested inside a list or map of objects (for example `podTemplate.spec.containers[].args`) now accept `null` as well as a list, matching how arrays elsewhere in the schema already behaved.
* The default Redpanda version installed by the chart is now
  [v26.2.6](https://github.com/redpanda-data/redpanda/releases/tag/v26.2.6),
  whose image no longer trusts the compromised eMudhra certificate authorities
  (CVE-2026-111943).
* Bump operator sidecar image tag to v26.2.5, which is built with Go 1.26.10
  and rejects certificates chaining to the compromised eMudhra certificate
  authorities (CVE-2026-111943).
### Fixed
* `config.rpk.tune_*: false` is honored again when `tuning.apply_host_tuners` is
  enabled. The host tuner defaults were merged over explicit `false` values, so
  every default-enabled tuner ran regardless of the opt-out (#1936).
* A broker could be left in maintenance mode after a rolling restart. The `postStart` lifecycle hook clears the maintenance mode the `preStop` hook enabled, but it is killed after half the termination grace period (45s by default), so when a broker took longer than that to start its admin API the hook never cleared it. The broker then held no partition leadership and kept the cluster's single maintenance-mode slot, so the next broker in the roll could not be drained before its restart. The hook now runs the clear in the background and returns immediately, and the clear keeps retrying until the broker's admin API is up. The `preStop` hook stops a clear that is still waiting before it drains the broker, so the clear cannot undo the drain. Maintenance mode enabled on a running broker, for example with `rpk cluster maintenance enable`, is still cleared only when the broker restarts. Containers after `redpanda` in the pod no longer wait for the hook to finish before they start.
