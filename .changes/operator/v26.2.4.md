## [v26.2.4](https://github.com/redpanda-data/redpanda-operator/releases/tag/operator%2Fv26.2.4) - 2026-09-23
### Changed
* Breaking change for Redpanda Connect pipelines, which are still in beta: the operator chart's `commonAnnotations` value is renamed to `connectAnnotations`, and the operator's `--common-annotations` flag to `--connect-annotations`. The value only ever annotated the resources the Connect Pipeline controller creates, never the operator chart's own objects, so the old name read as a chart-wide knob it never was. Rename it before upgrading: the chart's values schema rejects unknown keys, so the old name fails `helm upgrade` rather than being silently ignored.
### Fixed
* Setting `post_install_job.enabled=false` no longer prevents cluster configuration from being applied. It is now derived from chart values instead of the post-install job, so environment injected via `post_install_job.podTemplate` no longer feeds cluster config — use `config.extraClusterConfiguration` or `storage.tiered.credentialsSecretRef` instead.
* In the multicluster operator, a persistently failing maintenance-mode,
stale-disk-wipe, or decommission step no longer blocks a StretchCluster's
cluster-config and license synchronization; previously `ConfigurationApplied`
could report `True` indefinitely while spec changes were never applied.
* StretchCluster admin, Kafka, and Schema Registry clients no longer dial
broker pods on a node that has gone NotReady. Such pods keep their address
while being unreachable, previously wedging cluster-health fetches — and
with them decommission and pool cleanup — behind connection timeouts.
* StretchCluster clients keep at least two admin hosts: when endpoint
filtering leaves a single broker, the list is padded from the declared
endpoints so rpadmin retains leader resolution and try-every-host reads
instead of failing every request against one churning broker.
* Deleting a Redpanda or StretchCluster no longer waits for the 3-minute
periodic requeue before its finalizer is removed. While owned resources
are still being deleted the controller requeues every 10s instead of
relying on an incidental event.
* Objects rendered by the operator chart no longer carry `annotations: null` when no annotations are configured. ArgoCD compared that null against the live object's absent map and kept the ServiceMonitor (and every other chart object) permanently OutOfSync (#1085).
* The Console configuration rendered for a Redpanda resource no longer contains `kafka.sasl.enabled: true` and `kafka.sasl.impersonateUser: true` unless the legacy `console.console` block configured a login. Console 3.9 refuses to start with impersonation enabled while its own authentication is disabled, so clusters without SASL had a crash-looping Console.
* StatefulSet decommissioner fixes: the PersistentVolumeClaims of live brokers are no longer deleted during a rolling restart, and on Redpanda (v2) clusters the operator-wide decommissioner deletes claims only when `--auto-delete-pvcs` is set.

  The decommissioner resolved a StatefulSet's pods through the labels of the
  desired pod template. The template carries labels that change on every
  upgrade (`helm.sh/chart`), while the `OnDelete` update strategy leaves
  existing pods on the previous template's labels until they are rolled, so
  updating a StatefulSet made every not-yet-rolled pod invisible and their
  still-mounted claims looked orphaned. A claim seen unbound on two
  reconciles at least 30s apart was deleted; the affected pods then came
  back onto empty volumes and rejoined the cluster as new brokers. Pods are
  now matched with the StatefulSet's immutable `spec.selector`, which every
  pod of the StatefulSet satisfies regardless of template changes.

  The decommissioner started by `--additional-controllers=decommission` (or
  `all`) also deleted claims by default. It now does so only when
  `--auto-delete-pvcs` is passed, matching that flag's stated purpose.
  Operators relying on it to remove the claims a scale-down leaves behind
  must pass the flag.
