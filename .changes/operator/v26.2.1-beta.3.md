## [v26.2.1-beta.3](https://github.com/redpanda-data/redpanda-operator/releases/tag/operator%2Fv26.2.1-beta.3) - 2026-07-10
### Added
* Add Gateway API (HTTPRoute) support to Console CRD, allowing Console to be exposed via Gateway API controllers as an alternative to Ingress. Bumps sigs.k8s.io/gateway-api to v1.5.1.
* Adopted Redpanda 25.1+'s per-broker pre-restart probe as the primary
rolling-restart gate. The operator now consults /v1/broker/pre_restart_probe
for the specific broker it's about to roll, and proceeds only when the broker
reports no acks=1 data-loss risk, no produce/consume unavailability, and no
acks=-1 produce rejection. RF=1 offline is treated as acceptable risk. On
clusters older than 25.1 the helper detects 404 and falls back to the
cluster-wide IsHealthy heuristic so behavior on pre-25.1 brokers is unchanged.
The rolling-restart loop also consults the matching post-restart probe
(/v1/broker/post_restart_probe, load_reclaimed_pc) to verify each broker has
finished its post-restart replica recovery before the next pod is rolled; a
non-404 probe error fails closed (the roll is deferred rather than proceeding
without confirmation). The required caught-up percentage is configurable via
the --post-restart-caught-up-percent flag (default 100, i.e. full recovery;
validated to the range 1-100). These per-broker gates apply to both the
Redpanda (single-cluster) and StretchCluster (multicluster) reconcilers.

* Added an optional `namespace` field to `clusterRef` (used by `ShadowLink`, `Topic`, `User`, `Role`, `Schema`, and `Group` resources). When set, the referenced Redpanda/Cluster is resolved in that namespace instead of the referencing object's namespace, enabling cross-namespace references such as a `ShadowLink` whose source and shadow clusters live in separate namespaces on the same Kubernetes cluster. This same-cluster, cross-namespace topology is intended mainly for development and test clusters (cheaply rehearsing shadow-link replication and failover on a single Kubernetes cluster, optionally pinning the two clusters to non-overlapping availability zones); production disaster recovery should still place the source and shadow clusters in separate Kubernetes clusters and failure domains.
* Added optional anonymous cluster-shape telemetry: NodePools, stretch clusters, managed Connectors, Redpanda/vectorized cluster and broker counts, broker CPU/memory sizing, Redpanda versions in use, per-cluster TLS/SASL/tiered-storage/console adoption, storage CSI drivers, PVC Unbinder, CRD and supporting-CR counts, and operator feature flags. Licensed clusters additionally report the enterprise license checksum (id_hash) for account correlation. Disabled in builds without an embedded key and via the telemetry.enabled chart value / --disable-telemetry.
* Added a top-level `priorityClassName` value to the operator Helm chart. Set it
to a higher-priority PriorityClass so the Redpanda Operator Pod is less likely
to be preempted when the cluster is under resource pressure. Defaults to `""`
(the cluster's global default PriorityClass, if any).
* Operator releases now publish the `rpk-k8s` CLI as a managed rpk plugin. On each `operator/v*` release the per-OS/arch `rpk-k8s` binaries are uploaded to the rpk plugins repository (rpk-plugins.redpanda.com) with a generated manifest, so users can install and run it via `rpk k8s` (auto-downloaded, checksum-verified, and cached by rpk on first use).
* Add Broker CRD and minimal controller behind --enable-broker flag
* Support for Kubernetes versions 1.33.x through 1.36.x. Per-PR tests validate against the minimum supported version (1.33.x) and nightly tests validate against the maximum supported version (1.36.x).
* Added automatic recovery for brokers stuck in maintenance mode. A broker's
preStop hook enables maintenance mode before pod termination, but if the pod
cannot reschedule (e.g. its node is cordoned or lost), the postStart hook
that clears maintenance mode never runs, leaving the broker in maintenance
indefinitely. Because the Redpanda partition balancer excludes
maintenance-mode brokers from auto-decommission, this permanently blocked
recovery. The Redpanda (single-cluster) and StretchCluster (multicluster)
reconcilers now clear maintenance mode on any broker that has been in
maintenance, reported not-alive by the cluster, and whose pod has been
not-Ready for at least a configurable threshold (default 30m), unblocking
auto-decommission. The threshold is configurable via the new
--clear-maintenance-mode-after flag on both the `run` and `multicluster`
commands. A new maintenance_mode_cleared_total counter metric (labeled by
cluster) records each clear.

* Anonymous operator telemetry now reports how many Redpanda and StretchCluster resources have the opt-in chroot host tuners enabled (`spec.tuning.apply_host_tuners`), as `redpanda.hostTunersEnabled` and `stretchCluster.hostTunersEnabled`.
* The `StretchCluster` reconciler can now automatically recover a broker stuck in the "bad_rejoin" crashloop after a region outage (K8S-843) by wiping its stale disk: a decommissioned broker whose PVC survived boots from the stale disk, claims a retired identity, is rejected by the cluster, and never becomes Ready. When a broker pod stays not-Ready past a threshold AND its on-disk identity provably collides with the cluster's authoritative broker-uuid view, the operator deletes the pod's PVC and pod so it reschedules onto a fresh disk. This is destructive by design and heavily guarded: it fires only on a confirmed identity collision, sustained unreadiness, a healthy cluster, and zero nodes reported down, wiping at most one disk per reconcile pass. Tune the not-Ready threshold with `--wipe-stale-disk-after` (default 5m); set a negative value to disable the behavior entirely. This stale-disk wipe is distinct from the existing PVCUnbinder controller (`--unbind-pvcs-after`), which frees the PVCs of Pods stuck Pending on lost nodes.
### Changed
* `--additional-controllers=decommission` now runs the NodePool-aware `StatefulSetDecommissioner` operator-wide for V2 (`Redpanda`) clusters instead of the old `DecommissionReconciler`. It resolves each chart-rendered StatefulSet back to its `Redpanda` CR and builds the admin client from the chart-rendered DNS and is correct for clusters split across multiple NodePools. Operators already passing `--additional-controllers=decommission` (or `all`) are migrated to the new controller automatically on upgrade; no configuration change is required. `decommissionV2` is accepted as an alias.
* The Console controller now honors the `namespace` field of its `clusterSource.clusterRef`. Previously the renderer always resolved the referenced cluster in the Console's own namespace, so the `clusterRef.namespace` field exposed by the CRD was silently inert: a Console could fail to find the intended cluster, or — if a same-named cluster existed in its own namespace — silently bind to the wrong Redpanda and deploy against it. The lookup now uses `clusterRef.namespace` when set and falls back to the Console's namespace otherwise (no behavior change for same-namespace references). This covers `Redpanda`, `StretchCluster`, and v1 `Cluster` lookups.
* Controller reconcile (sync) intervals are now configurable on the operator instead of being hard-coded. New flags `--topic-sync-interval`, `--user-sync-interval`, `--group-sync-interval`, `--schema-sync-interval`, `--role-sync-interval`, and `--shadowlink-sync-interval` set the default reconcile cadence for each controller (Topic defaults to 30s; User/Group/Schema/Role/ShadowLink default to 5m). These are also exposed as first-class operator Helm chart values under `controllers.<resource>.interval` (named to match the `Topic` CR's `spec.interval`, rendered into the flags), in addition to `additionalCmdFlags`. The `Topic` CR continues to support a per-CR `spec.interval` that takes precedence over the operator default. As part of this, the `Topic` CRD no longer carries a baked-in `interval` default (previously `3s`); the default now lives in the operator. **This is introduced starting in the v26.2 operator.** Note on upgrade behavior: because the old CRD's `3s` default was applied by the API server at admission time, `Topic`s created under it already have `spec.interval: "3s"` persisted in etcd, and the controller treats any persisted `spec.interval` as an explicit per-CR override. Those existing `Topic`s therefore keep reconciling every 3s after upgrade — they do not automatically pick up the operator default. Only `Topic`s with no persisted `spec.interval` (i.e. created/applied against the new CRD, which has no baked-in default) inherit the operator default (30s, or whatever `--topic-sync-interval` is set to). To make a pre-existing `Topic` adopt the operator default, clear its stored value, e.g. `kubectl patch topic <name> --type=json -p='[{"op":"remove","path":"/spec/interval"}]'`; to pin a specific cadence instead, set `spec.interval` on the resource or adjust the flag/Helm value.
### Deprecated
* The old broker `DecommissionReconciler` is deprecated. It is no longer reached by `--additional-controllers=decommission` (which now runs the NodePool-aware `StatefulSetDecommissioner`); it remains available only as an opt-in escape hatch via `--additional-controllers=legacy-decommission` (excluded from `all`) for regression fallback and the Cloud Azure path, and will be removed in a future release. The operator logs a warning at startup when it is enabled.
### Removed
* Removed the `nodeWatcher` controller (`RedpandaNodePVCReconciler`). PVC remediation after node loss is now owned solely by the PVCUnbinder (`--unbind-pvcs-after`), which reacts to the actual unschedulable Pod and only touches non-remountable (local/hostPath) volumes. The `nodeWatcher` value for `--additional-controllers` is no longer recognized; deployments should remove it and rely on `--unbind-pvcs-after` instead.
### Fixed
* Fixed a scheme-registration gap that caused the controller-runtime cache
to error with `no kind "TLSRouteList" / "ListOptions" is registered for
version "gateway.networking.k8s.io/v1"` on every reconcile pass
whenever a Redpanda CR rendered TLSRoute objects via the chart's
Gateway API support. The chart's `Types()` now uses the upstream GA
`gatewayv1.TLSRoute` and the operator scheme registers the Gateway API v1
package, so List/Watch resolves correctly.

* Tightened the rolling restart gate so a single reconcile never deletes more than
one broker pod. The "pod has no matching broker in cluster view" branch used to
delete and continue, which meant a transient admin-API blip or address-format
mismatch could classify every pod as orphan and tear them all down in one pass —
now we delete one and requeue, and only while the cluster is healthy. The brokerMap
parser also strips a "host:port" suffix and keys by both the first DNS label and the
raw host, and pod lookup now falls back to the pod IP, so a broker advertising
"pod.svc:33145" or a bare-IP internal RPC address (e.g. stretch-cluster flat-network
mode) is recognized — for both rolling restart and scale-down decommission — instead
of being misclassified as an orphan. The same hardening now also applies to the
StretchCluster (multicluster) reconciler, which previously still ran the old
delete-all-orphans-at-once loop gated only on cluster-wide health.

* Fixed the operator-wide broker decommissioner (`--additional-controllers=decommission`) constructing the wrong broker Admin API hostname when `fullnameOverride` is set. It used the Helm release name for the Pod segment (`<release>-N.<fullname>...`) while the actual broker Pod is named from the chart fullname (`<fullname>-N.<fullname>...`), so the cluster-health check failed with `no such host` and decommission/PVC cleanup never completed. The Pod hostname now uses the fullname (honoring `fullnameOverride`); behavior is unchanged when `fullnameOverride` is unset.
* Made the broker-decommissioner (`StatefulSetDecommissioner`) NodePool/RedpandaBrokerPool aware. A cluster split across multiple StatefulSets (NodePools) now compares its total broker count against the sum of every pool's desired replicas when deciding whether brokers are in excess, and the per-pool scale-down decision uses each StatefulSet's own replicas and only acts on Pods belonging to that StatefulSet. Previously the decommissioner compared the cluster-wide broker count against a single StatefulSet's replicas and could evaluate the wrong pool's ordinals.
* Hardened the PVCUnbinder against multi-broker concurrent disruption. The unbinder used to act on each Pending broker pod in isolation, which during a K8s-wide event (cluster upgrade, AZ flake) could delete every broker's PVCs in parallel and — with `--allow-pv-rebinding=true` — let the scheduler cross-bind the freed PVs, leaving each broker with another broker's data. The reconcile now defers when (a) the parent CR carries the `operator.redpanda.com/pause-pvc-unbinder=true` annotation, (b) stuck pods span more than one node (auto-detected multi-node event), (c) a sibling pod's PVC is mid-recovery in the same cluster, or (d) a recent unbind in the same cluster hasn't yet been observed as settled through the informer cache. A new `--broker-pod-node-unavailable-toleration` flag injects long NotReady/Unreachable tolerations into broker pod templates so brief node unreachability no longer triggers the eviction → Pending → unbind chain in the first place. `--allow-pv-rebinding` is deprecated; the new gates make it unnecessary and unsafe.
* Topic controller no longer issues no-op `IncrementalAlterConfigs` on every reconcile: desired config values are now compared against the live broker config and only changed keys are written.
* Resource controllers (Topic, User, Group, Schema, Role, ShadowLink) no longer re-enqueue every CR on status-only updates of the referenced cluster CR. Cluster watches now filter to generation changes, so configured sync intervals (e.g. Topic `spec.interval`) take effect.
* Fixed `clusterSpec.statefulset.extraVolumeMounts`, `livenessProbe`, and `startupProbe` being silently dropped from the `redpanda` (broker) container — they previously only applied to the `sidecar` container.
* The rpk configuration inside broker pods no longer goes stale after brokers join or leave the cluster, in both the v1 (`Cluster` CRD) and v2 (`Redpanda` CRD) operators. Previously it was rendered once at pod startup, and because seed-server changes intentionally do not trigger rolling restarts, in-pod `rpk` kept whatever broker list existed when the pod started — e.g. a mix of old and new pool seed brokers after a NodePool blue/green migration. Both operators now refresh it restart-free from the kubelet-propagated ConfigMap mount, sharing a common watch loop: v1 broker pods gain a lightweight `rpk-profile-updater` sidecar that re-renders `/var/lib/redpanda/.config/rpk/rpk.yaml`, and the existing v2 sidecar gains `--watch-rpk-profile` (enabled by the chart), which re-grafts the `rpk:` stanza of `/etc/redpanda/redpanda.yaml` from the chart-rendered base-config while preserving the per-pod settings applied at startup. Note: the pod-template changes (new v1 container; new v2 sidecar mount/args) cause one rolling restart of clusters on operator/chart upgrade. Deployments that pin `--configurator-tag` (v1) or `sideCars.image.tag` (v2) to an older operator release must bump those pins to this release or later — the refresh runs in those images, and an older image does not recognize the new subcommand/flag.
* Fixed `clusterSpec.statefulset` overrides (probes, `extraVolumeMounts`) being silently dropped when `podTemplate.spec.containers` or `podTemplate.spec.initContainers` contains duplicate entries with the same name — conversion now applies overrides to the entry the chart actually renders (the last duplicate, matching the chart's merge semantics).
* Fixed `additionalCmdFlags` not being able to override the operator's default command-line flags in the rendered Deployment. Flags the chart sets a default for (e.g. `--enable-console`) were silently dropped in favor of the default; user-provided values now take precedence.
* Fixed User deletion getting stuck on clusters without an enterprise license.
Schema Registry ACL cleanup no longer issues a DeleteACLs request when there
are no ACLs to delete, which previously failed with "Invalid license: not
present" and prevented the finalizer from being removed.
* Multicluster `StretchCluster`: a peer that is registered with the manager but whose `StretchCluster` CR has been removed is no longer reported as `SpecSynced=ClusterUnreachable`. Such a peer is reachable — its CR is simply absent — so it is now treated as not participating: it is named distinctly in the condition message and no longer blocks the cluster from reaching `Stable` when the data plane is otherwise healthy.
* Multicluster `StretchCluster`: when SASL authentication is disabled, the `BootstrapUserSynced` condition is now set to a final `True` state (reason `Synced`) instead of being left at its default `Unknown`. Previously the bootstrap-user sync returned early without setting the condition, leaving it non-final, which blocked the `Quiesced` aggregate — and therefore `Stable` — from ever reaching `True` on an otherwise healthy cluster.
* Multicluster `StretchCluster`: `PoolTracker` no longer drops the canonical cluster name from the pods it selects for a rolling restart or from the StatefulSets it creates, scales, or updates. These previously carried an empty canonical cluster name, so the operator logged a blank cluster identifier for those operations in stretch/multicluster deployments. Construction now goes through helpers that require the canonical cluster name, preventing the omission from recurring.
* The Redpanda and `StretchCluster` reconcilers no longer stall cluster-level recovery when no broker is Ready. Previously the pool reconciler aborted the reconcile pass whenever the cluster had no Ready broker, so during a full-region outage — where every surviving broker's readiness probe fails on under-replicated partitions — the operator could never run the very recovery steps needed to heal the cluster: clearing stuck maintenance mode and decommissioning (both reconcilers), plus the stale-disk wipe (StretchCluster only). The "no broker Ready yet" fast requeue is now applied at the end of the reconcile instead of aborting it.
* The operator chart now grants the operator ServiceAccount `nodes:
get/list/watch` (in the `additional-controllers` ClusterRole, gated by
`rbac.createAdditionalControllerCRs`). Previously the operator held
`nodes: get` only, so Kubernetes RBAC escalation prevention rejected
the per-pool rack-awareness ClusterRole the StretchCluster renderer
creates (`is attempting to grant RBAC permissions not currently
held`), and a StretchCluster with `rackAwareness.enabled: true` could
not deploy from a default chart install.
* RedpandaBrokerPool `tls.enabled: false` now disables TLS on the
defaulted external listeners too. Previously the rendered
redpanda.yaml kept `kafka_api_tls` / `admin_api_tls` /
`pandaproxy_api_tls` / `schema_registry_api_tls` entries pointing at
`/etc/tls/certs/external/*` (which nothing mounts when pool TLS is
off), and brokers crash-looped with "Could not read trust file"
unless every listener carried an explicit fully-shaped TLS-off
override. Additionally, `clusterRef.group` values containing a
version suffix (e.g. `cluster.redpanda.com/v1alpha2`) are now
rejected by CRD validation instead of silently never binding the
referencing object.
* The User CRD now accepts `spec.authentication.password.value` on its
own, as documented. The schema previously marked
`password.valueFrom` as unconditionally required, so the structural
check rejected value-only manifests before the either/or validation
rule could run. Providing neither `value` nor `valueFrom` is still
rejected, now with the rule's own message.
