## [v25.3.10](https://github.com/redpanda-data/redpanda-operator/releases/tag/operator%2Fv25.3.10) - 2026-09-24
### Added
* `podTemplate` now applies to every workload the chart renders — the operator
  Deployment, the CRD installation Job, and the post-upgrade migration Job —
  rather than the Deployment alone.

  New `deployment.podTemplate`, `jobs.crd.podTemplate`, and
  `jobs.migration.podTemplate` layer per-workload overrides on top of it,
  making the hook Jobs' container `securityContext` configurable.

  Pod templates are merged using a form of strategic merge patch that keys on
  unique names as defined by Kubernetes. For example: to apply container
  specific overrides specify the name of the container you're targeting:

  ```yaml
  deployment:
    podTemplate:
      spec:
        containers:
        - name: manager # Targets the operators manager container
          securityContext: { ... }
  ```

  As a consequence of the widened scope, both Jobs now inherit
  `podTemplate`'s default pod `securityContext` (`runAsUser: 65532`), which
  previously reached only the Deployment.

  Fixes [#1287](https://github.com/redpanda-data/redpanda-operator/issues/1287).
### Fixed
* Setting `post_install_job.enabled=false` no longer prevents cluster
  configuration from being applied. It is now derived from chart values
  instead of the post-install job, so environment injected via
  `post_install_job.podTemplate` no longer feeds cluster config — use
  `config.extraClusterConfiguration` or `storage.tiered.credentialsSecretRef`
  instead.
* The Console configuration rendered for a Redpanda resource no longer
  contains `kafka.sasl.enabled: true` and `kafka.sasl.impersonateUser: true`
  unless the legacy `console.console` block configured a login. Console 3.9
  refuses to start with impersonation enabled while its own authentication is
  disabled, so clusters without SASL had a crash-looping Console.
