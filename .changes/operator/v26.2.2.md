## [v26.2.2](https://github.com/redpanda-data/redpanda-operator/releases/tag/operator%2Fv26.2.2) - 2026-08-14
### Fixed
* The operator now recovers brokers wedged by the redpanda#31057 leader-restart ghost and by decommissioned-broker bad_rejoin crashloops (K8S-843), on single-cluster and StretchCluster resources, with or without persistent storage.

  When a broker loses its data directory, or is decommissioned as collateral of
  the redpanda#31057 leader-restart wedge, it can boot a retired on-disk identity,
  be refused by the controller ("bad_rejoin"), and crashloop — while a leaked
  maintenance-mode flag blocks the auto-decommission that would resolve it. The
  operator now handles this end to end:

    - Ghost maintenance clear: a leaked maintenance flag on a dead broker whose
      address a live successor already owns is cleared immediately. For the
      leader-restart case, where no successor can register until the flag is
      gone, the operator asks the pod at the ghost's address which node id it is
      actually running and clears the flag once a different, assigned id proves
      the ghost can never rejoin.
    - Stale-disk wipe: a broker whose on-disk identity collides with the
      cluster's authoritative membership and has stayed not-Ready past a
      threshold (`--wipe-stale-disk-after`) has its data-dir PVC (if any) and
      pod deleted so it reschedules with a fresh identity. This destructive
      recovery is opt-in on the single-cluster operator — disabled by default
      there, enabled by setting a positive duration — while the StretchCluster
      operator keeps its existing 5m default; 0 or a negative value disables
      it. The ghost maintenance clear above is unaffected by this flag and
      always runs. Without persistent storage the identity
      lives in the pod's emptyDir, so the wipe degrades to deleting just the pod.
      When the broker's admin API never binds — a crashloop cannot finish cluster
      discovery — a kubelet-attributed pod-log fallback supplies the same
      identity plus the cluster's own refusal verdict.

    Every destructive action is heavily guarded. Authoritative membership, uuid,
    and health reads (and maintenance-mode writes) are pinned to the CONTROLLER
    LEADER, which cannot lag its own committed membership, so a stale or lagging
    broker can never make a live member look retired; the operator confirms the
    pinned node still agrees it is the leader and defers if no leader is
    reachable rather than trusting an unpinned view. A wipe additionally requires
    a confirmed identity collision, sustained not-Readiness, a healthy cluster
    with zero nodes down (re-checked immediately before deletion), and the same
    retired identity re-confirmed across passes; the answering broker's
    advertised address must belong to the dialed pod; only the StatefulSet's own
    data-dir claims are deleted (never other PVCs the pod mounts); a candidate
    whose pod was recreated (UID changed) or whose data dir is a hostPath the
    wipe cannot reset is skipped; and a broker mid `node_id_overrides` migration
    is deferred by identity so its data is preserved. Requires a new `pods/log`
    get RBAC (included in the generated roles).
* The StretchCluster preStop lifecycle hook no longer stalls pod termination — or SIGTERMs a broker mid-drain — and bounds its admin API calls.

  Enabling maintenance mode on a broker whose node id is no longer a cluster
  member (e.g. one decommissioned during the redpanda#31057 recovery) answers
  404 forever; the hook now skips the drain on a 404 instead of retrying until
  its timeout (a 400 — the single maintenance slot is busy — still retries, which
  is what serializes drains across a rolling restart). The drain-completion poll
  now waits until draining has actually begun before accepting draining=false, so
  a broker is never SIGTERMed while still holding all its leadership; the node-id
  lookup that precedes the drain is bounded so a crashlooping broker whose admin
  API never binds no longer spins the whole grace period; and every admin-API
  curl in the hooks carries a per-request timeout. StretchCluster StatefulSets
  render their lifecycle hooks from the operator, so the redpanda chart's
  equivalent fix does not cover them.
* CRD installation no longer fails on Kubernetes versions that enforce CEL reserved-word escaping (observed on 1.31).

  The Pipeline CRD's `cluster.clusterRef.namespace` validation rule spelled the
  field unescaped; `namespace` is a CEL reserved word, so stricter apiservers
  rejected the CRD at admission — and because the CRD installer is
  all-or-nothing, fresh installs of operator v26.2.1 with `crds.enabled=true`
  could not bootstrap. The rule now uses `__namespace__`, valid on all
  supported Kubernetes versions.
* All nodepools after the first no longer inherit the first nodepool's cluster.redpanda.com/nodepool label.

  The internal label-union helper mutated its first argument in place and
  returned that same map by reference instead of a copy. ForCluster passed the
  Cluster CR's own Labels map through it as that first argument, so every call
  to ForCluster for a given cluster handed back that identical live map. Once
  Helm's app.kubernetes.io/managed-by: Helm label made the map non-nil, the
  first nodepool to derive its labels from it stamped
  cluster.redpanda.com/nodepool directly into the shared map, and the union
  helper's "existing key wins" rule then made every subsequent nodepool
  silently inherit that same stale value instead of its own — so all of a
  later nodepool's pods carried an earlier nodepool's label. The union helper
  now always allocates and returns a new map and never touches either input,
  so no caller can observe or propagate a mutation through it.
* Fixed the operator chart's `ServiceMonitor` and the StretchCluster per-pool `ServiceMonitor`s to emit `scheme: http` / `scheme: https` (lowercase) instead of the uppercase Go constant values that older `prometheus-operator` CRDs reject with `spec.endpoints[0].scheme: Unsupported value`. Same fix as #1511, which covered the redpanda and console charts.
* Fixed the post-upgrade migration job failing the whole upgrade when its ServiceAccount lacks permissions for optional resource types swept during field-manager migration — e.g. Gateway API `tlsroutes`/`httproutes` on clusters that have the Gateway API CRDs installed but manage RBAC manually (`rbac.create=false`). `Forbidden` errors during the sweep are now logged as warnings and the affected type or resource is skipped (and re-swept on the next upgrade); failing to list the `Redpanda`/`Console` custom resources themselves remains fatal.
* Official release images now embed the telemetry signing key, enabling operator telemetry.

  The release pipeline fetched `TELEMETRY_PRIVATE_KEY` on the Buildkite agent
  but never forwarded it into the containerized build
  (`ci/scripts/run-in-nix-docker.sh` forwards env vars by explicit allowlist),
  so the key-injection step silently no-op'd, `key.pem` stayed empty, and the
  telemetry client was compiled out (a disabled no-op) of every published
  image, including v26.2.1 and its betas.
