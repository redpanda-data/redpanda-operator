## [v26.2.2](https://github.com/redpanda-data/redpanda-operator/releases/tag/operator%2Fv26.2.2) - 2026-08-14
### Fixed
* The operator now recovers brokers wedged by the redpanda#31057 leader-restart ghost and by decommissioned-broker bad_rejoin crashloops (K8S-843), on single-cluster and StretchCluster resources, with or without persistent storage.

  When a broker loses its data directory, or is decommissioned as collateral of
  the redpanda#31057 leader-restart wedge, it can boot a retired on-disk identity,
  be refused by the controller ("bad_rejoin"), and crashloop — while a leaked
  maintenance-mode flag blocks the auto-decommission that would resolve it. The
  operator now handles this end to end:

    - Ghost maintenance clear: a leaked maintenance flag on a dead broker whose
      address a live successor already owns is cleared immediately. For the
      leader-restart case, where no successor can register until the flag is
      gone, the operator asks the pod at the ghost's address which node id it is
      actually running and clears the flag once a different, assigned id proves
      the ghost can never rejoin.
    - Stale-disk wipe: a broker whose on-disk identity collides with the
      cluster's authoritative membership and has stayed not-Ready past a
      threshold (`--wipe-stale-disk-after`) has its data-dir PVC (if any) and
      pod deleted so it reschedules with a fresh identity. This destructive
      recovery is opt-in on the single-cluster operator — disabled by default
      there, enabled by setting a positive duration — while the StretchCluster
      operator keeps its existing 5m default; 0 or a negative value disables
      it. The ghost maintenance clear above is unaffected by this flag and
      always runs. Without persistent storage the identity
      lives in the pod's emptyDir, so the wipe degrades to deleting just the pod.
      When the broker's admin API never binds — a crashloop cannot finish cluster
      discovery — a kubelet-attributed pod-log fallback supplies the same
      identity plus the cluster's own refusal verdict.

    Every destructive action is heavily guarded. Authoritative membership, uuid,
    and health reads (and maintenance-mode writes) are pinned to the CONTROLLER
    LEADER, which cannot lag its own committed membership, so a stale or lagging
    broker can never make a live member look retired; the operator confirms the
    pinned node still agrees it is the leader and defers if no leader is
    reachable rather than trusting an unpinned view. A wipe additionally requires
    a confirmed identity collision, sustained not-Readiness, a healthy cluster
    with zero nodes down (re-checked immediately before deletion), and the same
    retired identity re-confirmed across passes; the answering broker's
    advertised address must belong to the dialed pod; only the StatefulSet's own
    data-dir claims are deleted (never other PVCs the pod mounts); a candidate
    whose pod was recreated (UID changed) or whose data dir is a hostPath the
    wipe cannot reset is skipped; and a broker mid `node_id_overrides` migration
    is deferred by identity so its data is preserved. Requires a new `pods/log`
    get RBAC (included in the generated roles).
* The StretchCluster preStop lifecycle hook no longer stalls pod termination — or SIGTERMs a broker mid-drain — and bounds its admin API calls.

  Enabling maintenance mode on a broker whose node id is no longer a cluster
  member (e.g. one decommissioned during the redpanda#31057 recovery) answers
  404 forever; the hook now skips the drain on a 404 instead of retrying until
  its timeout (a 400 — the single maintenance slot is busy — still retries, which
  is what serializes drains across a rolling restart). The drain-completion poll
  now waits until draining has actually begun before accepting draining=false, so
  a broker is never SIGTERMed while still holding all its leadership; the node-id
  lookup that precedes the drain is bounded so a crashlooping broker whose admin
  API never binds no longer spins the whole grace period; and every admin-API
  curl in the hooks carries a per-request timeout. StretchCluster StatefulSets
  render their lifecycle hooks from the operator, so the redpanda chart's
  equivalent fix does not cover them.
* CRD installation no longer fails on Kubernetes versions that enforce CEL reserved-word escaping (observed on 1.31).

  The Pipeline CRD's `cluster.clusterRef.namespace` validation rule spelled the
  field unescaped; `namespace` is a CEL reserved word, so stricter apiservers
  rejected the CRD at admission — and because the CRD installer is
  all-or-nothing, fresh installs of operator v26.2.1 with `crds.enabled=true`
  could not bootstrap. The rule now uses `__namespace__`, valid on all
  supported Kubernetes versions.
* All nodepools after the first no longer inherit the first nodepool's cluster.redpanda.com/nodepool label.

  The internal label-union helper mutated its first argument in place and
  returned that same map by reference instead of a copy. ForCluster passed the
  Cluster CR's own Labels map through it as that first argument, so every call
  to ForCluster for a given cluster handed back that identical live map. Once
  Helm's app.kubernetes.io/managed-by: Helm label made the map non-nil, the
  first nodepool to derive its labels from it stamped
  cluster.redpanda.com/nodepool directly into the shared map, and the union
  helper's "existing key wins" rule then made every subsequent nodepool
  silently inherit that same stale value instead of its own — so all of a
  later nodepool's pods carried an earlier nodepool's label. The union helper
  now always allocates and returns a new map and never touches either input,
  so no caller can observe or propagate a mutation through it.
* Fixed the operator chart's `ServiceMonitor` and the StretchCluster per-pool `ServiceMonitor`s to emit `scheme: http` / `scheme: https` (lowercase) instead of the uppercase Go constant values that older `prometheus-operator` CRDs reject with `spec.endpoints[0].scheme: Unsupported value`. Same fix as #1511, which covered the redpanda and console charts.
* Fixed the post-upgrade migration job failing the whole upgrade when its ServiceAccount lacks permissions for optional resource types swept during field-manager migration — e.g. Gateway API `tlsroutes`/`httproutes` on clusters that have the Gateway API CRDs installed but manage RBAC manually (`rbac.create=false`). `Forbidden` errors during the sweep are now logged as warnings and the affected type or resource is skipped (and re-swept on the next upgrade); failing to list the `Redpanda`/`Console` custom resources themselves remains fatal.
* Official release images now embed the telemetry signing key, enabling operator telemetry.

  The release pipeline fetched `TELEMETRY_PRIVATE_KEY` on the Buildkite agent
  but never forwarded it into the containerized build
  (`ci/scripts/run-in-nix-docker.sh` forwards env vars by explicit allowlist),
  so the key-injection step silently no-op'd, `key.pem` stayed empty, and the
  telemetry client was compiled out (a disabled no-op) of every published
  image, including v26.2.1 and its betas.

## [v26.2.1](https://github.com/redpanda-data/redpanda-operator/releases/tag/operator%2Fv26.2.1) - 2026-07-28
### Added
* Beta support for stretch clusters. The new StretchCluster resource lets you deploy the operator across multiple Kubernetes clusters and build a single Redpanda cluster from RedpandaBrokerPool resources in different clusters, so your Redpanda cluster can survive the loss of an entire Kubernetes cluster or region. Requires a valid Redpanda Enterprise license.
* Multicluster-aware leader election. You can now run multiple operator replicas in the same Kubernetes cluster for high availability. All replicas take part in the global Raft quorum, but only the replica holding the local lease votes.
* The PVC unbinder controller now works in multicluster mode, so remediation for stuck Pods and volume-affinity problems covers every member cluster, not just the local one.
* Every operator replica now caches the kubeconfigs of its peer clusters, so a newly elected leader can start managing peer clusters immediately instead of waiting on live connections to every other operator.
* The RedpandaBrokerPool CRD is installed automatically when you deploy the operator in multicluster mode. You can also use it to manage broker pools in a single Kubernetes cluster.
* The operator now creates a Service for each peer, so the multicluster Raft transport works in cluster mesh setups such as Multi-Cluster Services (MCS) or Cilium global services.
* Added Gateway API (HTTPRoute) support to the Console CRD, allowing Console to be exposed via Gateway API controllers as an alternative to Ingress. Bumps sigs.k8s.io/gateway-api to v1.5.1.
* Adopted Redpanda 25.1+'s per-broker pre-restart probe as the primary rolling-restart gate. The operator now consults /v1/broker/pre_restart_probe for the specific broker it's about to roll, and proceeds only when the broker reports no acks=1 data-loss risk, no produce/consume unavailability, and no acks=-1 produce rejection. RF=1 offline is treated as acceptable risk. On clusters older than 25.1 the helper detects 404 and falls back to the cluster-wide IsHealthy heuristic so behavior on pre-25.1 brokers is unchanged. The rolling-restart loop also consults the matching post-restart probe (/v1/broker/post_restart_probe, load_reclaimed_pc) to verify each broker has finished its post-restart replica recovery before the next pod is rolled; a non-404 probe error fails closed (the roll is deferred rather than proceeding without confirmation). The required caught-up percentage is configurable via the --post-restart-caught-up-percent flag (default 100, i.e. full recovery; validated to the range 1-100). These per-broker gates apply to both the Redpanda (single-cluster) and StretchCluster (multicluster) reconcilers.
* Added an optional `namespace` field to `clusterRef` (used by `ShadowLink`, `Topic`, `User`, `Role`, `Schema`, and `Group` resources). When set, the referenced Redpanda/Cluster is resolved in that namespace instead of the referencing object's namespace, enabling cross-namespace references such as a `ShadowLink` whose source and shadow clusters live in separate namespaces on the same Kubernetes cluster. This same-cluster, cross-namespace topology is intended mainly for development and test clusters (cheaply rehearsing shadow-link replication and failover on a single Kubernetes cluster, optionally pinning the two clusters to non-overlapping availability zones); production disaster recovery should still place the source and shadow clusters in separate Kubernetes clusters and failure domains.
* Added optional anonymous cluster-shape telemetry: NodePools, stretch clusters, managed Connectors, Redpanda/vectorized cluster and broker counts, broker CPU/memory sizing, Redpanda versions in use, per-cluster TLS/SASL/tiered-storage/console adoption, storage CSI drivers, PVC Unbinder, CRD and supporting-CR counts, and operator feature flags. Licensed clusters additionally report the enterprise license checksum (id_hash) for account correlation. Disabled in builds without an embedded key and via the telemetry.enabled chart value / --disable-telemetry.
* Added a top-level `priorityClassName` value to the operator Helm chart. Set it to a higher-priority PriorityClass so the Redpanda Operator Pod is less likely to be preempted when the cluster is under resource pressure. Defaults to `""` (the cluster's global default PriorityClass, if any).
* Operator releases now publish the `rpk-k8s` CLI as a managed rpk plugin. On each `operator/v*` release the per-OS/arch `rpk-k8s` binaries are uploaded to the rpk plugins repository (rpk-plugins.redpanda.com) with a generated manifest, so users can install and run it with `rpk k8s` (auto-downloaded, checksum-verified, and cached by rpk on first use). Use `rpk k8s multicluster bootstrap` to generate the TLS certificates and peer configuration for a Redpanda stretch cluster. Use `rpk k8s multicluster bundle` to collect cross-cluster operator diagnostics (per-peer Pod, Deployment, TLS, and Raft status, logs, and multiple `/metrics` samples) into a single zip file; it discovers all peers from labeled kubeconfig cache Secrets when you provide any one peer's kubeconfig. The chart also binds the operator ServiceAccount to the `metrics-reader` ClusterRole so the bundle (and the existing ServiceMonitor) can scrape `/metrics` without permission errors.
* Support for Kubernetes versions 1.33.x through 1.36.x. Per-PR tests validate against the minimum supported version (1.33.x) and nightly tests validate against the maximum supported version (1.36.x).
* Added automatic recovery for brokers stuck in maintenance mode. A broker's preStop hook enables maintenance mode before pod termination, but if the pod cannot reschedule (e.g. its node is cordoned or lost), the postStart hook that clears maintenance mode never runs, leaving the broker in maintenance indefinitely. Because the Redpanda partition balancer excludes maintenance-mode brokers from auto-decommission, this permanently blocked recovery. The Redpanda (single-cluster) and StretchCluster (multicluster) reconcilers now clear maintenance mode on any broker that has been in maintenance, reported not-alive by the cluster, and whose pod has been not-Ready for at least a configurable threshold (default 30m), unblocking auto-decommission. The threshold is configurable via the new --clear-maintenance-mode-after flag on both the `run` and `multicluster` commands. A new maintenance_mode_cleared_total counter metric (labeled by cluster) records each clear.
* Anonymous operator telemetry now reports how many Redpanda and StretchCluster resources have the opt-in chroot host tuners enabled (`spec.tuning.apply_host_tuners`), as `redpanda.hostTunersEnabled` and `stretchCluster.hostTunersEnabled`.
* The `StretchCluster` reconciler can now automatically recover a broker stuck in the "bad_rejoin" crashloop after a region outage by wiping its stale disk: a decommissioned broker whose PVC survived boots from the stale disk, claims a retired identity, is rejected by the cluster, and never becomes Ready. When a broker pod stays not-Ready past a threshold AND its on-disk identity provably collides with the cluster's authoritative broker-uuid view, the operator deletes the pod's PVC and pod so it reschedules onto a fresh disk. This is destructive by design and heavily guarded: it fires only on a confirmed identity collision, sustained unreadiness, a healthy cluster, and zero nodes reported down, wiping at most one disk per reconcile pass. Tune the not-Ready threshold with `--wipe-stale-disk-after` (default 5m); set a negative value to disable the behavior entirely. This stale-disk wipe is distinct from the existing PVCUnbinder controller (`--unbind-pvcs-after`), which frees the PVCs of Pods stuck Pending on lost nodes.
* Added a `Broker` custom resource and reconciler (experimental, behind the `--enable-broker` flag): per-broker pod/PVC lifecycle with grant-gated serialized rotation, leadership drain, node_id continuity verification, explicit-intent decommission with recommission and last-broker guard, dead-node PV remediation (honors --unbind-pvcs-after when set, 5m default otherwise), and full status conditions.
* ShadowLink resources now expose `spec.clientOptions` for tuning the Kafka client the shadow cluster uses to fetch from the source cluster: `fetchMinBytes`, `fetchWaitMaxMs`, `fetchMaxBytes`, `fetchPartitionMaxBytes`, `metadataMaxAgeMs`, `connectionTimeoutMs`, and `retryBackoffMs`. These primarily trade replication latency against fetch batching efficiency. Each field is left at the broker default when unset (or set to 0), so existing ShadowLinks are unaffected.
* ShadowLink now replicates RBAC roles and schemas from the source cluster by default. A new `spec.roleSyncOptions` section controls role replication (`enabled`, `interval`, `paused`, and `roleNameFilters`, which default to a single include-all filter), and `spec.schemaRegistrySyncOptions` gained an `enabled` toggle that defaults to shadowing the source cluster's schemas topic. Set `enabled: false` on either section to turn the replication off.

  Schemas can also be replicated from an external schema registry (for example a Confluent Schema Registry) over its REST API via the new `spec.schemaRegistrySyncOptions.shadowSchemaRegistryAPI` section, which supports the source URL, TLS settings, sync intervals, a source context/subject filter, context mappings, and an unsupported schema feature policy. The HTTP basic authentication credentials — the schema registry API key (username) and API secret (password) — may reference Kubernetes Secrets.
* Added the `Pipeline` CRD and Connect controller (**Beta**; enterprise, opt-in via `--enable-connect` / the chart's `connectController.enabled`): declarative Redpanda Connect pipelines with inline `configYaml`, `cluster.clusterRef`/`cluster.staticConfiguration` connection resolution (including ConfigMap truststores and mTLS client certificates), `userRef` SCRAM identities, `valueSources`, `extraInitContainers` + `extraVolumes`/`extraVolumeMounts`, `affinity`, the scale subresource (`kubectl scale`, HorizontalPodAutoscaler, and KEDA drive `.spec.replicas` directly), PodMonitor support, and pod-template checksums that roll pipeline pods on config changes and on referenced Secret/ConfigMap rotations. The resolved cluster connection is rendered both into `input.redpanda`/`output.redpanda` blocks and as the top-level `redpanda:` shared client (redpanda_common support). Referenced Users, password Secrets, and valueSources are validated at reconcile time and surface on dedicated status conditions (`ClusterRef`, `UserRef`, `ValueSourcesResolved`, `License`); reconcile failures surface on status without tearing down running pipelines, and the controller refuses to adopt same-named objects it does not own (`NameConflict`). Default Connect image: 4.101.0.
* You can now import existing Redpanda users into operator management. Set `spec.authentication.syncCredentials` to keep a user's credentials in sync when an external tool, such as External Secrets Operator (ESO), rotates the password Secret.
* Added end-to-end operator observability for the multicluster operator. (1) Multicluster raft metrics under `operator_multicluster_raft_*` — leader changes, sent/received message rates by type and peer, send latency / errors / drops, peer reachability, snapshot bookkeeping, plus collector-emitted gauges for current term, state, and per-peer send-queue length read on scrape from the transport's atomics so the Ready loop hot path stays write-free. (2) Reconcile-health metrics under `operator_controller_*` — `reconcile_steady_state_total` (counter) and `reconcile_last_success_timestamp_seconds` (gauge), wrapper-emitted automatically for every controller via `observability.Wrap(reconciler, controller, defaultRequeueTimeout)`. Both `(Result{}, nil)` and `(Result{RequeueAfter: defaultRequeueTimeout}, nil)` count as steady state so controllers using the periodic-requeue pattern (e.g. `MulticlusterReconciler`'s defer-set `RequeueAfter`) register as healthy. (3) StretchCluster member-status metrics under `operator_stretchcluster_*` — `member_reachable`, `brokers` / `brokers_ready`, `replication_health`, `spec_drift`, recorded by the `MulticlusterReconciler` alongside data it already computes (background reachability probe, NodePool fetch, `checkSpecConsistency`, admin API health check) — no new RPCs. New `monitoring.rulesEnabled` chart value ships a starter PrometheusRule with recording rules and alerts covering errored reconciles, runaway reconcile rate, stalled controllers, worker pool saturation, member unreachability, broker count skew, spec drift, and unhealthy replication. Comprehensive single-view Grafana dashboard at `docs/operator-grafana-dashboard.json`; canonical metric inventory at `docs/operator-metrics.md`.
* The Redpanda Console controller is now registered in multicluster operator mode, and `Console.spec.cluster.clusterRef` can resolve `kind: StretchCluster`, so operator-managed Console deployments work in StretchCluster setups. The Console controller previously did not run when the operator was started via `multicluster`, which silently dropped any `cluster.redpanda.com/v1alpha2 Console` CR applied alongside a `StretchCluster`.
* Added `scrapeInterval` and `labels` fields to the operator Helm chart's `monitoring` configuration. `scrapeInterval` sets the scrape interval on the ServiceMonitor endpoint (defaults to empty, preserving the Prometheus global default). `labels` adds custom labels to the ServiceMonitor metadata.
* Added `persistentVolumeClaimRetentionPolicy` to the Redpanda CRD (`spec.clusterSpec.statefulset.persistentVolumeClaimRetentionPolicy`) and to the NodePool CRD (`spec.persistentVolumeClaimRetentionPolicy`) so PVCs can be deleted automatically when brokers are decommissioned via scale-down or when the cluster is torn down. The Redpanda CRD value applies as the default for every NodePool (default and named); a NodePool's own value, if set, overrides the cluster-level default.
### Changed
* Attempts to unset `redpanda.storage.mode` on a Topic are now a no-op to avoid warn-level log spam in the broker.
* Bumped Go to 1.26.5, controller-runtime to the matching release, and updated a range of dependencies (OpenTelemetry, grpc, containerd, golang.org/x/net, go-chi, buger/jsonparser) to address Snyk and govulncheck findings.
* The Redpanda Connect controller can now be enabled via the operator Helm chart by setting `connectController.enabled: true`. The controller is disabled by default. The enterprise license is configured at the operator level via `enterprise.licenseSecretRef` in the Helm chart values.

  To enable the Connect controller:

  ```
  helm install redpanda-operator redpanda/operator \
    --set connectController.enabled=true \
    --set enterprise.licenseSecretRef.name=redpanda-license \
    --set enterprise.licenseSecretRef.key=license
  ```

* `--additional-controllers=decommission` now runs the NodePool-aware `StatefulSetDecommissioner` operator-wide for V2 (`Redpanda`) clusters instead of the old `DecommissionReconciler`. It resolves each chart-rendered StatefulSet back to its `Redpanda` CR and builds the admin client from the chart-rendered DNS and is correct for clusters split across multiple NodePools. Operators already passing `--additional-controllers=decommission` (or `all`) are migrated to the new controller automatically on upgrade; no configuration change is required. `decommissionV2` is accepted as an alias.
* The Console controller now honors the `namespace` field of its `clusterSource.clusterRef`. Previously the renderer always resolved the referenced cluster in the Console's own namespace, so the `clusterRef.namespace` field exposed by the CRD was silently inert: a Console could fail to find the intended cluster, or — if a same-named cluster existed in its own namespace — silently bind to the wrong Redpanda and deploy against it. The lookup now uses `clusterRef.namespace` when set and falls back to the Console's namespace otherwise (no behavior change for same-namespace references). This covers `Redpanda`, `StretchCluster`, and v1 `Cluster` lookups.
* Controller reconcile (sync) intervals are now configurable on the operator instead of being hard-coded. New flags `--topic-sync-interval`, `--user-sync-interval`, `--group-sync-interval`, `--schema-sync-interval`, `--role-sync-interval`, and `--shadowlink-sync-interval` set the default reconcile cadence for each controller (Topic defaults to 30s; User/Group/Schema/Role/ShadowLink default to 5m). These are also exposed as first-class operator Helm chart values under `controllers.<resource>.interval` (named to match the `Topic` CR's `spec.interval`, rendered into the flags), in addition to `additionalCmdFlags`. The `Topic` CR continues to support a per-CR `spec.interval` that takes precedence over the operator default. As part of this, the `Topic` CRD no longer carries a baked-in `interval` default (previously `3s`); the default now lives in the operator. **This is introduced starting in the v26.2 operator.** Note on upgrade behavior: because the old CRD's `3s` default was applied by the API server at admission time, `Topic`s created under it already have `spec.interval: "3s"` persisted in etcd, and the controller treats any persisted `spec.interval` as an explicit per-CR override. Those existing `Topic`s therefore keep reconciling every 3s after upgrade — they do not automatically pick up the operator default. Only `Topic`s with no persisted `spec.interval` (i.e. created/applied against the new CRD, which has no baked-in default) inherit the operator default (30s, or whatever `--topic-sync-interval` is set to). To make a pre-existing `Topic` adopt the operator default, clear its stored value, e.g. `kubectl patch topic <name> --type=json -p='[{"op":"remove","path":"/spec/interval"}]'`; to pin a specific cadence instead, set `spec.interval` on the resource or adjust the flag/Helm value.
* **Upgrade behavior change for existing ShadowLinks.** Role and schema replication now default to on (see the corresponding "Added" entry). Because these defaults are applied by the conversion layer whenever the `spec.roleSyncOptions` / `spec.schemaRegistrySyncOptions` sections are absent or leave `enabled` unset, **any ShadowLink created before this release will begin replicating all RBAC roles (via an include-all filter) and shadowing the source cluster's schemas topic on the first reconcile after upgrade** — no spec change is required to trigger this. Roles may include privileged or superuser roles, so operators should treat this as an expansion of what is replicated to the shadow (DR) cluster. To preserve the previous behavior, explicitly set `spec.roleSyncOptions.enabled: false` and/or `spec.schemaRegistrySyncOptions.enabled: false` on existing ShadowLinks **before** upgrading the operator.
* The SASL mechanism fields on the Redpanda and StretchCluster CRDs (`auth.sasl.mechanism`, `auth.sasl.bootstrapUser.mechanism`, and `auth.sasl.users[].mechanism`) now have enum validation restricting them to `SCRAM-SHA-256` or `SCRAM-SHA-512`, matching the chart's values schema. Previously an invalid or misspelled mechanism was admitted and then surfaced only later as recurring Kafka-API reconcile errors; it is now rejected at apply time. Note: this is a stricter CRD. Kubernetes validates enums only on write, so existing objects are not re-checked at upgrade, but the next `kubectl apply`/update of an object whose mechanism holds a non-canonical value — including an explicit empty string (`mechanism: ""`), which the operator previously treated as "use the default" — will be rejected. Audit and correct such values (or omit the field to get the default) before or after upgrading.

### Deprecated
* The old broker `DecommissionReconciler` is deprecated. It is no longer reached by `--additional-controllers=decommission` (which now runs the NodePool-aware `StatefulSetDecommissioner`); it remains available only as an opt-in escape hatch via `--additional-controllers=legacy-decommission` (excluded from `all`) for regression fallback and the Cloud Azure path, and will be removed in a future release. The operator logs a warning at startup when it is enabled.
### Removed
* Removed the `nodeWatcher` controller (`RedpandaNodePVCReconciler`). PVC remediation after node loss is now owned solely by the PVCUnbinder (`--unbind-pvcs-after`), which reacts to the actual unschedulable Pod and only touches non-remountable (local/hostPath) volumes. The `nodeWatcher` value for `--additional-controllers` is no longer recognized; deployments should remove it and rely on `--unbind-pvcs-after` instead.
### Fixed
* The Helm-to-operator migration job now removes the `helm` field manager, along with other historic field managers that caused conflicts when the operator updated StatefulSets after a migration from the Helm chart.
* Fixed an issue with post-upgrade processing of cluster configuration that resulted in configuration errors due to removed properties across Redpanda versions.
* Fixed ballast file tuning: the tuning container now mounts the correct directory, so the ballast file reaches the main Redpanda container.
* Fixed hot reconcile loops on healthy Redpanda clusters driven by two independent root causes: the `setStatusCondition` helper treated a zero rate limit as "force an update" (because `time.Since(anything) > 0` is always true), and non-deterministic map iteration over `features.Features` flipped the stored `InUseFeatures` value on every reconcile. `InUseFeatures` is now sorted before comparison, the zero-rate-limit case is handled correctly, and the condition heartbeat rate limit was stretched from 1 minute to 5 minutes. Rate-limited heartbeats for License and Configuration conditions are preserved.
* Fixed an issue where the operator failed to authenticate to the Redpanda cluster with SCRAM when `bootstrapUser.secretKeyRef` pointed at an externally-managed secret.
* Fixed Schema Registry ACL sync failures on v1alpha1 `Cluster` resources that configured SR via the legacy single `schemaRegistry` field instead of the `schemaRegistryApi` slice — `SchemaRegistryInternalListener` now checks both fields and the factory routes the no-SR case to the graceful skip path.
* Fixed namespace-scoped operator deployments logging reconcile errors for resources in other namespaces; non-matching namespaces are now filtered before the initial fetch instead of entering exponential backoff.
* Fixed StretchCluster partial deletion causing cross-cluster resource destruction. When a StretchCluster was deleted from a subset of clusters, the reconciler would destroy resources on surviving clusters and leave the cluster in an unrecoverable state. Added a partial deletion guard that blocks cleanup when the StretchCluster is still active on other clusters, and scoped cross-cluster sync operations (SyncAll, syncBootstrapUser, syncCA) to skip clusters where the StretchCluster is being deleted.
* Fixed a hot reconcile loop on healthy Redpanda clusters where the operator would re-enqueue itself every ~2 seconds instead of settling into the 3-minute periodic requeue interval. The setStatusCondition helper treated a zero rate limit as "force an update" (because time.Since(anything) > 0 is always true), which bumped lastTransitionTime on every pass and triggered a status write for conditions that had not actually changed. Rate-limited heartbeats for License and Configuration conditions are preserved.
* The StretchCluster admin API client now honors the Factory.WithAdminClientTimeout setting on all code paths (previously silently dropped), and the multicluster binary exposes a --cluster-connection-timeout flag to configure it.
* Fixed a deadlock where an unhealthy cluster could not recover by adding more broker pods. Scale-up operations in node pools are no longer gated on cluster health; only scale-down (decommission) operations remain gated.
* Fixed a misleading Cluster CR status condition when the operator could not resolve an external secret referenced from cluster config (e.g. an iceberg REST catalog OAuth2 client secret). Previously, the failure was silently downgraded to a warning, the unexpanded ${secrets.X} placeholder was pushed to the Redpanda admin API, and Redpanda's downstream validation error ("Must set both of iceberg_rest_catalog_client_id ...") surfaced as the condition message — obscuring the real cause (e.g. an AccessDeniedException from the cloud secret store). The reconcile now fails before pushing config, with the unresolved-secret warning as the actionable condition message. Shared code path between Operator v1 and v2.
* Fixed a scheme-registration gap that caused the controller-runtime cache to error with `no kind "TLSRouteList" / "ListOptions" is registered for version "gateway.networking.k8s.io/v1"` on every reconcile pass whenever a Redpanda CR rendered TLSRoute objects via the chart's Gateway API support. The chart's `Types()` now uses the upstream GA `gatewayv1.TLSRoute` and the operator scheme registers the Gateway API v1 package, so List/Watch resolves correctly.
* Tightened the rolling restart gate so a single reconcile never deletes more than one broker pod. The "pod has no matching broker in cluster view" branch used to delete and continue, which meant a transient admin-API blip or address-format mismatch could classify every pod as orphan and tear them all down in one pass — now we delete one and requeue, and only while the cluster is healthy. The brokerMap parser also strips a "host:port" suffix and keys by both the first DNS label and the raw host, and pod lookup now falls back to the pod IP, so a broker advertising "pod.svc:33145" or a bare-IP internal RPC address (e.g. stretch-cluster flat-network mode) is recognized — for both rolling restart and scale-down decommission — instead of being misclassified as an orphan. The same hardening now also applies to the StretchCluster (multicluster) reconciler, which previously still ran the old delete-all-orphans-at-once loop gated only on cluster-wide health.
* Fixed the operator-wide broker decommissioner (`--additional-controllers=decommission`) constructing the wrong broker Admin API hostname when `fullnameOverride` is set. It used the Helm release name for the Pod segment (`<release>-N.<fullname>...`) while the actual broker Pod is named from the chart fullname (`<fullname>-N.<fullname>...`), so the cluster-health check failed with `no such host` and decommission/PVC cleanup never completed. The Pod hostname now uses the fullname (honoring `fullnameOverride`); behavior is unchanged when `fullnameOverride` is unset.
* Made the broker-decommissioner (`StatefulSetDecommissioner`) NodePool/RedpandaBrokerPool aware. A cluster split across multiple StatefulSets (NodePools) now compares its total broker count against the sum of every pool's desired replicas when deciding whether brokers are in excess, and the per-pool scale-down decision uses each StatefulSet's own replicas and only acts on Pods belonging to that StatefulSet. Previously the decommissioner compared the cluster-wide broker count against a single StatefulSet's replicas and could evaluate the wrong pool's ordinals.
* Hardened the PVCUnbinder against multi-broker concurrent disruption. The unbinder used to act on each Pending broker pod in isolation, which during a K8s-wide event (cluster upgrade, AZ flake) could delete every broker's PVCs in parallel and — with `--allow-pv-rebinding=true` — let the scheduler cross-bind the freed PVs, leaving each broker with another broker's data. The reconcile now defers when (a) the parent CR carries the `operator.redpanda.com/pause-pvc-unbinder=true` annotation, (b) stuck pods span more than one node (auto-detected multi-node event), (c) a sibling pod's PVC is mid-recovery in the same cluster, or (d) a recent unbind in the same cluster hasn't yet been observed as settled through the informer cache. A new `--broker-pod-node-unavailable-toleration` flag injects long NotReady/Unreachable tolerations into broker pod templates so brief node unreachability no longer triggers the eviction → Pending → unbind chain in the first place. `--allow-pv-rebinding` is deprecated; the new gates make it unnecessary and unsafe.
* Topic controller no longer issues no-op `IncrementalAlterConfigs` on every reconcile: desired config values are now compared against the live broker config and only changed keys are written.
* Resource controllers (Topic, User, Group, Schema, Role, ShadowLink) no longer re-enqueue every CR on status-only updates of the referenced cluster CR. Cluster watches now filter to generation changes, so configured sync intervals (e.g. Topic `spec.interval`) take effect.
* Fixed `clusterSpec.statefulset.extraVolumeMounts`, `livenessProbe`, and `startupProbe` being silently dropped from the `redpanda` (broker) container — they previously only applied to the `sidecar` container.
* The rpk configuration inside broker pods no longer goes stale after brokers join or leave the cluster, in both the v1 (`Cluster` CRD) and v2 (`Redpanda` CRD) operators. Previously it was rendered once at pod startup, and because seed-server changes intentionally do not trigger rolling restarts, in-pod `rpk` kept whatever broker list existed when the pod started — e.g. a mix of old and new pool seed brokers after a NodePool blue/green migration. Both operators now refresh it restart-free from the kubelet-propagated ConfigMap mount, sharing a common watch loop: v1 broker pods gain a lightweight `rpk-profile-updater` sidecar that re-renders `/var/lib/redpanda/.config/rpk/rpk.yaml`, and the existing v2 sidecar gains `--watch-rpk-profile` (enabled by the chart), which re-grafts the `rpk:` stanza of `/etc/redpanda/redpanda.yaml` from the chart-rendered base-config while preserving the per-pod settings applied at startup. Note: the pod-template changes (new v1 container; new v2 sidecar mount/args) cause one rolling restart of clusters on operator/chart upgrade. Deployments that pin `--configurator-tag` (v1) or `sideCars.image.tag` (v2) to an older operator release must bump those pins to this release or later — the refresh runs in those images, and an older image does not recognize the new subcommand/flag.
* Fixed `clusterSpec.statefulset` overrides (probes, `extraVolumeMounts`) being silently dropped when `podTemplate.spec.containers` or `podTemplate.spec.initContainers` contains duplicate entries with the same name — conversion now applies overrides to the entry the chart actually renders (the last duplicate, matching the chart's merge semantics).
* Fixed `additionalCmdFlags` not being able to override the operator's default command-line flags in the rendered Deployment. Flags the chart sets a default for (e.g. `--enable-console`) were silently dropped in favor of the default; user-provided values now take precedence.
* Fixed User deletion getting stuck on clusters without an enterprise license. Schema Registry ACL cleanup no longer issues a DeleteACLs request when there are no ACLs to delete, which previously failed with "Invalid license: not present" and prevented the finalizer from being removed.
* Multicluster `StretchCluster`: a peer that is registered with the manager but whose `StretchCluster` CR has been removed is no longer reported as `SpecSynced=ClusterUnreachable`. Such a peer is reachable — its CR is simply absent — so it is now treated as not participating: it is named distinctly in the condition message and no longer blocks the cluster from reaching `Stable` when the data plane is otherwise healthy.
* Multicluster `StretchCluster`: when SASL authentication is disabled, the `BootstrapUserSynced` condition is now set to a final `True` state (reason `Synced`) instead of being left at its default `Unknown`. Previously the bootstrap-user sync returned early without setting the condition, leaving it non-final, which blocked the `Quiesced` aggregate — and therefore `Stable` — from ever reaching `True` on an otherwise healthy cluster.
* Multicluster `StretchCluster`: `PoolTracker` no longer drops the canonical cluster name from the pods it selects for a rolling restart or from the StatefulSets it creates, scales, or updates. These previously carried an empty canonical cluster name, so the operator logged a blank cluster identifier for those operations in stretch/multicluster deployments. Construction now goes through helpers that require the canonical cluster name, preventing the omission from recurring.
* The Redpanda and `StretchCluster` reconcilers no longer stall cluster-level recovery when no broker is Ready. Previously the pool reconciler aborted the reconcile pass whenever the cluster had no Ready broker, so during a full-region outage — where every surviving broker's readiness probe fails on under-replicated partitions — the operator could never run the very recovery steps needed to heal the cluster: clearing stuck maintenance mode and decommissioning (both reconcilers), plus the stale-disk wipe (StretchCluster only). The "no broker Ready yet" fast requeue is now applied at the end of the reconcile instead of aborting it.
* The operator chart now grants the operator ServiceAccount `nodes: get/list/watch` on multicluster installs (in the `additional-controllers` ClusterRole, gated by `rbac.createAdditionalControllerCRs` and `multicluster.enabled`). Previously the operator held `nodes: get` only, so Kubernetes RBAC escalation prevention rejected the per-pool rack-awareness ClusterRole the StretchCluster renderer creates (`is attempting to grant RBAC permissions not currently held`), and a StretchCluster with `rackAwareness.enabled: true` could not deploy from a default chart install.
* RedpandaBrokerPool `tls.enabled: false` now disables TLS on the defaulted external listeners too. Previously the rendered redpanda.yaml kept `kafka_api_tls` / `admin_api_tls` / `pandaproxy_api_tls` / `schema_registry_api_tls` entries pointing at `/etc/tls/certs/external/*` (which nothing mounts when pool TLS is off), and brokers crash-looped with "Could not read trust file" unless every listener carried an explicit fully-shaped TLS-off override. Additionally, `clusterRef.group` values containing a version suffix (e.g. `cluster.redpanda.com/v1alpha2`) are now rejected by CRD validation instead of silently never binding the referencing object.
* The User CRD now accepts `spec.authentication.password.value` on its own, as documented. The schema previously marked `password.valueFrom` as unconditionally required, so the structural check rejected value-only manifests before the either/or validation rule could run. Providing neither `value` nor `valueFrom` is still rejected, now with the rule's own message.
* The PVCUnbinder's pvc-rebinding gate (Gate 3) no longer defers on unbound claims owned by Pods that are provably deadlocked on the unbinder's own remediation. Treating those claims as in-progress rebinds deadlocked clusters that use WaitForFirstConsumer binding — a stuck Pod's unbound claim can never bind until the Pod schedules, the Pod can never schedule until its mis-pinned sibling claim is unbound, and the gate deferred exactly that unbind forever. A fresh cluster whose broker's shadow-index-cache PV was provisioned onto an already-occupied node never bootstrapped, with the unbinder logging "a PVC in this cluster has no volumeName yet; deferring" every 30s; the exemption is symmetric so multiple simultaneously mis-pinned brokers cannot mutually deadlock either. The exemption applies only under a strict proof chain: the Pod is stuck Pending past the unbind timeout, holds a Bound claim on a HostPath/Local PV whose every eligible node is provably unavailable (gone, cordoned, NotReady/unreachable net of unconditional tolerations — pods under --broker-pod-node-unavailable-toleration=-1s never treat transient unreachability as loss — or occupied by a pod matched by the stuck Pod's own hard hostname-scoped anti-affinity), the unbound claim resolves to a WaitForFirstConsumer StorageClass, and the reconciled Pod additionally holds its own mis-pin proof before any deletion proceeds. The occupancy-based proof requires a hard (Required) anti-affinity term scoped to the kubernetes.io/hostname topology in the pod's own namespace with no matchLabelKeys — terms are judged by that shape whether statefulset.podAntiAffinity type "hard" or "custom" produced them, while type "soft" yields no required terms and never qualifies (the other proof legs — node gone, cordoned, or unreachable — still apply); clusters deadlocked purely on an occupied node without such a term keep deferring, visible via the pvc-rebinding gate metric and Event. The two-victims-on-two-nodes variant of the same mis-provisioning is a known remaining gap: it defers at the multi-node gate instead and still requires manual PVC deletion. Orphaned claims with no Pod keep deferring the unbind, unbinder-initiated rebinds stay serialized by the in-flight gate's uncached settle check, the deferral log/Event now names the gating claim, every exemption-based gate pass that proceeds to remediation is recorded by a Warning PVCUnbinderGateExempted Event, a log line, and the new pvc_unbinder_gate_exempted_total metric (a pass still held by the freed-pv gate records that gate's deferral instead), and under the deprecated --allow-pv-rebinding flag the original conservative behavior (no exemption at all) is kept because freed Available PVs make acting while any claim is unbound unsafe. A new --disable-pvc-rebinding-gate-exemption flag (operator and sidecar; in the redpanda chart set `statefulset.sideCars.pvcUnbinder.disableStuckClaimExemption`) turns just the exemption off as an escape hatch while keeping the rest of the unbinder running. The unbinder's ClusterRole additionally grants nodes list and storageclasses get for the exemption's evidence reads; if RBAC is managed out-of-band and lags the upgrade, evidence reads fall back to the conservative deferral (fail-safe) rather than erroring.
* The operator now clears maintenance mode on ghost brokers: dead broker ids that were superseded by a live broker advertising the same address under a different node id (a pod that lost its data directory and rejoined the cluster). This remediates clusters that already leaked maintenance state before the `postStart` hook fix, without requiring a pod restart. Detection requires a stable advertised DNS address shared between the ghost and its successor; brokers advertising bare pod IPs (flat-network mode) are never matched, since a reused pod IP is not a stable identity.
* Fixed a StretchCluster deadlock where applying the same manifest to every member cluster at once (a scripted loop or a GitOps controller such as Argo or Flux) could persist divergent bootstrap-user passwords across clusters, tripping the leader's consistency check and permanently halting reconciliation with `Cluster has no desired brokers`. Because the Secret is immutable the cluster could not self-heal. The multicluster renderer no longer generates its own bootstrap-user password; creation and cross-cluster synchronization of the Secret is now owned exclusively by the reconciler's single-writer `syncBootstrapUser` path. The password-mismatch error message now also reports the local cluster by its canonical name instead of an empty string.
* StretchCluster now honors `spec.auth.sasl.bootstrapUser.secretKeyRef`. Previously the field was silently ignored: the operator always created and read its own generated `<name>-bootstrap-user` Secret, so automation that supplied a password via the documented `secretKeyRef` failed to authenticate. The reconciler now reads a pre-existing password from the referenced Secret/key (or writes a generated one there) and replicates it to every member cluster, and the broker StatefulSet, admin/Kafka client, and static-config conversion all resolve the credential from the same location.
* StretchCluster bootstrap-user sync now fails loudly instead of silently diverging when a user-provided `bootstrapUser.secretKeyRef` points at a Secret that exists but has no data under the referenced key. Previously the reconciler ignored the empty key, generated a fresh password, and wrote it only to the member clusters that lacked the Secret — splitting credentials across the stretch. It now sets a terminal `BootstrapUserSynced` error condition asking the operator to populate the referenced key.
* StretchClusters bootstrapped before `bootstrapUser.secretKeyRef` was honored no longer break operator authentication when a secretKeyRef is added later. Such a cluster was bootstrapped with the operator-managed `<name>-bootstrap-user` Secret, and the bootstrap password cannot be changed by editing a Secret. The reconciler now detects the legacy Secret, keeps using the password the cluster was actually bootstrapped with, and seeds the referenced secretKeyRef location from it. If the referenced location already holds a different password it refuses with a terminal condition instead of writing divergent copies across member clusters.
* Fixed SASL authentication on StretchClusters using the default SCRAM mechanism. The operator's internal Kafka client hardcoded SCRAM-SHA-256 while the bootstrap user (kubernetes-controller) is provisioned with the mechanism from spec.auth.sasl.mechanism, which defaults to SCRAM-SHA-512. This caused every operator operation going through the Kafka API (User CRs, ACL sync) to fail with SASL_AUTHENTICATION_FAILED. The client now derives its SCRAM mechanism from the cluster spec. Note: the bootstrap user's SCRAM credential is created once at first boot, so `auth.sasl.mechanism` is effectively immutable — changing it on an already-bootstrapped cluster leaves the stored credential under the old mechanism and re-triggers the same authentication failure.
* StretchCluster lifecycle hooks now clear maintenance mode left behind by a previous incarnation of the pod that re-registered under a different node id, matching the equivalent `charts/redpanda` `postStart` fix. Stretch StatefulSets render their hooks from the operator, not the chart, so they previously relied solely on the reconciler backstop for ghost remediation.
* The multicluster StretchCluster controller no longer renders broker StatefulSets and ConfigMaps when a configured peer cluster's BrokerPool list wasn't observed this reconcile pass — whether the peer was probe-unreachable, its list call failed, or its runtime registration hadn't completed yet (e.g. a brief post-leader-election window before the engage cycle and bootstrap peer registration finish). Previously the renderer could compute `seed_servers` from an incomplete cross-cluster pool view, producing a self-only seed list for a freshly added RedpandaBrokerPool. A broker that bootstraps from a self-only seed list forms its own standalone cluster instead of joining the existing StretchCluster, causing a split-brain. Only the pool-derived steps (CA sync and resource rendering) are deferred and retried; cluster-level recovery — maintenance-mode clearing, stale-disk wipe, decommission hygiene, and license/config sync — keeps running on reachable members during the deferral.
* Changing `spec.authentication.type` on an existing `User` now rewrites the user's SCRAM credential under the newly requested SASL mechanism. Redpanda stores a single credential per user, mechanism included, but the operator only checked whether the user existed at all, so the credential belonging to the previous mechanism made the change look as though it had already been applied. Nothing was written: clients using the newly requested mechanism failed with `SASL_AUTHENTICATION_FAILED` (or a `401 Unauthorized` from Schema Registry, where it reads like a missing subject ACL), while clients still pinned to the previous mechanism kept working and the `User` reported `Synced=True` — which is what made the drift easy to miss.

  Note the corollary when upgrading: for a `User` whose `type` was edited but never took effect, the first reconcile after this fix applies the change for real, and the credential under the previous mechanism stops working at that point. Migrate clients to the requested mechanism before upgrading.

  Deletion now removes the mechanisms the cluster actually holds rather than the one implied by the spec. Previously, deleting a `User` whose stored mechanism differed from its spec — including a spec with `authentication` removed, which implies SCRAM-SHA-512 — could leave a live credential orphaned in the cluster and strand the finalizer retrying.

  On brokers too old to support the Kafka SCRAM describe API the stored mechanism cannot be observed, so the previous behavior is preserved there: a `type` change is still not detected.

### Added
* Add Gateway API (HTTPRoute) support to Console CRD, allowing Console to be exposed via Gateway API controllers as an alternative to Ingress. Bumps sigs.k8s.io/gateway-api to v1.5.1.

rolling-restart gate. The operator now consults /v1/broker/pre_restart_probe
for the specific broker it's about to roll, and proceeds only when the broker
reports no acks=1 data-loss risk, no produce/consume unavailability, and no
acks=-1 produce rejection. RF=1 offline is treated as acceptable risk. On
clusters older than 25.1 the helper detects 404 and falls back to the
cluster-wide IsHealthy heuristic so behavior on pre-25.1 brokers is unchanged.
The rolling-restart loop also consults the matching post-restart probe
(/v1/broker/post_restart_probe, load_reclaimed_pc) to verify each broker has

non-404 probe error fails closed (the roll is deferred rather than proceeding
without confirmation). The required caught-up percentage is configurable via
the --post-restart-caught-up-percent flag (default 100, i.e. full recovery;
validated to the range 1-100). These per-broker gates apply to both the
Redpanda (single-cluster) and StretchCluster (multicluster) reconcilers.

This same-cluster, cross-namespace topology is intended mainly for development and test clusters (cheaply rehearsing shadow-link replication and failover on a single Kubernetes cluster, optionally pinning the two clusters to non-overlapping availability zones); production disaster recovery should still place the source and shadow clusters in separate Kubernetes clusters and failure domains.

Disabled in builds without an embedded key and via the telemetry.enabled chart value / --disable-telemetry.

to a higher-priority PriorityClass so the Redpanda Operator Pod is less likely
to be preempted when the cluster is under resource pressure. Defaults to `""`
(the cluster's global default PriorityClass, if any).

preStop hook enables maintenance mode before pod termination, but if the pod
cannot reschedule (e.g. its node is cordoned or lost), the postStart hook
that clears maintenance mode never runs, leaving the broker in maintenance
indefinitely. Because the Redpanda partition balancer excludes
maintenance-mode brokers from auto-decommission, this permanently blocked
recovery. The Redpanda (single-cluster) and StretchCluster (multicluster)

The unbinder used to act on each Pending broker pod in isolation, which during a K8s-wide event (cluster upgrade, AZ flake) could delete every broker's PVCs in parallel and — with `--allow-pv-rebinding=true` — let the scheduler cross-bind the freed PVs, leaving each broker with another broker's data. The reconcile now defers when (a) the parent CR carries the `operator.redpanda.com/pause-pvc-unbinder=true` annotation, (b) stuck pods span more than one node (auto-detected multi-node event), (c) a sibling pod's PVC is mid-recovery in the same cluster, or (d) a recent unbind in the same cluster hasn't yet been observed as settled through the informer cache. A new `--broker-pod-node-unavailable-toleration` flag injects long NotReady/Unreachable tolerations into broker pod templates so brief node unreachability no longer triggers the eviction → Pending → unbind chain in the first place. `--allow-pv-rebinding` is deprecated; the new gates make it unnecessary and unsafe.
* Topic controller no longer issues no-op `IncrementalAlterConfigs` on every reconcile: desired config values are now compared against the live broker config and only changed keys are written.
* Resource controllers (Topic, User, Group, Schema, Role, ShadowLink) no longer re-enqueue every CR on status-only updates of the referenced cluster CR. Cluster watches now filter to generation changes, so configured sync intervals (e.g. Topic `spec.interval`) take effect.
* Fixed `clusterSpec.statefulset.extraVolumeMounts`, `livenessProbe`, and `startupProbe` being silently dropped from the `redpanda` (broker) container — they previously only applied to the `sidecar` container.
* The rpk configuration inside broker pods no longer goes stale after brokers join or leave the cluster, in both the v1 (`Cluster` CRD) and v2 (`Redpanda` CRD) operators. Previously it was rendered once at pod startup, and because seed-server changes intentionally do not trigger rolling restarts, in-pod `rpk` kept whatever broker list existed when the pod started — e.g. a mix of old and new pool seed brokers after a NodePool blue/green migration. Both operators now refresh it restart-free from the kubelet-propagated ConfigMap mount, sharing a common watch loop: v1 broker pods gain a lightweight `rpk-profile-updater` sidecar that re-renders `/var/lib/redpanda/.config/rpk/rpk.yaml`, and the existing v2 sidecar gains `--watch-rpk-profile` (enabled by the chart), which re-grafts the `rpk:` stanza of `/etc/redpanda/redpanda.yaml` from the chart-rendered base-config while preserving the per-pod settings applied at startup. Note: the pod-template changes (new v1 container; new v2 sidecar mount/args) cause one rolling restart of clusters on operator/chart upgrade. Deployments that pin `--configurator-tag` (v1) or `sideCars.image.tag` (v2) to an older operator release must bump those pins to this release or later — the refresh runs in those images, and an older image does not recognize the new subcommand/flag.
* Fixed `clusterSpec.statefulset` overrides (probes, `extraVolumeMounts`) being silently dropped when `podTemplate.spec.containers` or `podTemplate.spec.initContainers` contains duplicate entries with the same name — conversion now applies overrides to the entry the chart actually renders (the last duplicate, matching the chart's merge semantics).
* Fixed `additionalCmdFlags` not being able to override the operator's default command-line flags in the rendered Deployment. Flags the chart sets a default for (e.g. `--enable-console`) were silently dropped in favor of the default; user-provided values now take precedence.
* Fixed User deletion getting stuck on clusters without an enterprise license.
Schema Registry ACL cleanup no longer issues a DeleteACLs request when there
are no ACLs to delete, which previously failed with "Invalid license: not
present" and prevented the finalizer from being removed.
* Multicluster `StretchCluster`: a peer that is registered with the manager but whose `StretchCluster` CR has been removed is no longer reported as `SpecSynced=ClusterUnreachable`. Such a peer is reachable — its CR is simply absent — so it is now treated as not participating: it is named distinctly in the condition message and no longer blocks the cluster from reaching `Stable` when the data plane is otherwise healthy.
* Multicluster `StretchCluster`: when SASL authentication is disabled, the `BootstrapUserSynced` condition is now set to a final `True` state (reason `Synced`) instead of being left at its default `Unknown`. Previously the bootstrap-user sync returned early without setting the condition, leaving it non-final, which blocked the `Quiesced` aggregate — and therefore `Stable` — from ever reaching `True` on an otherwise healthy cluster.
* Multicluster `StretchCluster`: `PoolTracker` no longer drops the canonical cluster name from the pods it selects for a rolling restart or from the StatefulSets it creates, scales, or updates. These previously carried an empty canonical cluster name, so the operator logged a blank cluster identifier for those operations in stretch/multicluster deployments. Construction now goes through helpers that require the canonical cluster name, preventing the omission from recurring.
* The Redpanda and `StretchCluster` reconcilers no longer stall cluster-level recovery when no broker is Ready. Previously the pool reconciler aborted the reconcile pass whenever the cluster had no Ready broker, so during a full-region outage — where every surviving broker's readiness probe fails on under-replicated partitions — the operator could never run the very recovery steps needed to heal the cluster: clearing stuck maintenance mode and decommissioning (both reconcilers), plus the stale-disk wipe (StretchCluster only). The "no broker Ready yet" fast requeue is now applied at the end of the reconcile instead of aborting it.
* The operator chart now grants the operator ServiceAccount `nodes:
get/list/watch` (in the `additional-controllers` ClusterRole, gated by
`rbac.createAdditionalControllerCRs`). Previously the operator held
`nodes: get` only, so Kubernetes RBAC escalation prevention rejected
the per-pool rack-awareness ClusterRole the StretchCluster renderer
creates (`is attempting to grant RBAC permissions not currently
held`), and a StretchCluster with `rackAwareness.enabled: true` could
not deploy from a default chart install.
* RedpandaBrokerPool `tls.enabled: false` now disables TLS on the
defaulted external listeners too. Previously the rendered
redpanda.yaml kept `kafka_api_tls` / `admin_api_tls` /
`pandaproxy_api_tls` / `schema_registry_api_tls` entries pointing at
`/etc/tls/certs/external/*` (which nothing mounts when pool TLS is
off), and brokers crash-looped with "Could not read trust file"
unless every listener carried an explicit fully-shaped TLS-off
override. Additionally, `clusterRef.group` values containing a
version suffix (e.g. `cluster.redpanda.com/v1alpha2`) are now
rejected by CRD validation instead of silently never binding the
referencing object.
* The User CRD now accepts `spec.authentication.password.value` on its
own, as documented. The schema previously marked
`password.valueFrom` as unconditionally required, so the structural
check rejected value-only manifests before the either/or validation
rule could run. Providing neither `value` nor `valueFrom` is still
rejected, now with the rule's own message.

  `chartRef` now defaults to v5.9.19.
  When `useFlux` is `false`, the equivalent of chart v5.9.19 will be deployed.

* Bumped the internal chart version to v5.9.20.
* [Chart] Moved all template rendering into `entry-point.yaml` to match the redpanda and console charts.
* The redpanda operator's helm chart has been merged into the operator itself.

  Going forward the chart's `version` and `appVersion` will always be equal.
### Removed
* Removed bundled FluxCD controllers, bundled FluxCD CRDs, and support for delegating control to FluxCD.

  Previously reconciled FluxCD resources (`HelmRepository`, `HelmRelease`)
  will **NOT** be garbage collected upon upgrading. If the operator is
  coexisting with a FluxCD installation, please take care to manually remove
  the left over resources.

  `chartRef.useFlux: true` and `chartRef.chartVersion` are no longer
  supported. The controller will log errors and abort reconcilation until the
  fields are unset. Ensure that both have been removed from all `Redpanda`
  resources before upgrading.

  All other `chartRef` fields are deprecated and are no longer referenced.

  `helmRelease`, `helmReleaseReady`, `helmRepository`, `helmRepositoryReady`,
  and `upgradeFailures` are no longer set on `RedpandaStatus`, similar to their
  behavior when `useFlux: false` was set.
* `gcr.io/kubebuilder/kube-rbac-proxy` container is deprecated and has been removed from the Redpanda
operator helm chart. The same ports will continue to serve metrics using kubebuilder's built in RBAC.

Any existing prometheus rules don't need to be adjusted.

For more details see: https://github.com/kubernetes-sigs/kubebuilder/discussions/3907

* The V1 operator now requires a minimum Redpanda version of 23.2; all feature-gated behaviour that supported older versions is now enabled unconditionally.
### Fixed
* Usage of `tpl` and `include` now function as expected when `useFlux: false` is set.

  `{{ (get (fromJson (include "redpanda.Fullname" (dict "a" (list .)))) "r") }}` would previously failure with fairly arcane errors.

  Now, the above example will correctly render to a string value. However,
  syntax errors and the like are still reported in an arcane fashion.

* Toggling `useFlux`, in either direction, no longer causes the bootstrap user's password to be regenerated.

  Manual mitigation steps are available [here](https://github.com/redpanda-data/helm-charts/issues/1596#issuecomment-2628356953).
* Certificate reloading for webhook and metrics endpoints should now behave correctly.
* Expanded the set of rules in both Roles and ClusterRoles to be appropriately in sync with the redpanda helm chart.

## v2.3.6-24.3.3 - 2025-01-17
### Added
* Users in air-gapped environments that cannot access the official Redpanda Helm Chart repository (`https://charts.redpanda.com/`)
  can now specify an alternative Helm chart repository using the `helm-repository-url` flag. In the Redpanda Operator Helm chart,
  this flag is not exposed as an option in the Helm values. Instead, it must be set as an input in the `additionalCmdFlags` array.
  
  The given repository must include the following charts:
  * Redpanda
  * Console
  * Connectors

* Added `resources.limits` and `resources.requests` as an alternative method of managing the redpanda container's resources.

  When both `resources.limits` and `resources.requests` are specified, the
  redpanda container's `resources` will be set to the provided values and all
  other keys of `resources` will be ignored. Instead, all other values will be
  inferred from the limits and requests.

  This allows fine grain control of resources. i.e. It is now possible to set
  CPU requests without setting limits:

  ```yaml
  resources:
    limits: {} # Specified but no cpu or memory values provided
    requests:
      cpu: 5 # Only CPU requests
  ```

### Changed
* For any user that is mirroring configurator image (air-gapped environment) and changes entrypoint
  or wraps configurator with additional script the following constraint need to be meet:
  * set the following flags
    * to change the container repository set `--configurator-base-image=my.repo.com/configurator` flag
    * to change the container tag set `--configurator-tag=XYZ` flag
  * image needs to supports the entrypoint `redpanda-operator configure` as it is the default one

### Fixed
* Value's merging no longer writes files to disk which prevents the operator from eating disk space when the reconciliation loop is run in rapid succession
* Fixed slice out of bounds panics when using the fs-validator and `useFlux: false`
